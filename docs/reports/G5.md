### 首要失败：普通页面笔记输入导致整个 App 退出

安装版与冻结 Debug 都从示例插件的正常文字输入路径触发，不涉及异常插件或权限绕过。实际先正常打开书、启用并打开「页面笔记」、确认面板显示页名和尺寸，然后点击笔记框输入普通文本。两次安装版和一次 Debug 均退出，有系统 `.ips` 报告。第二次安装版及 Debug 仅按一个字母 `a` 即触发。

| 时间（本机） | 构建 | PID | 结果 |
|---|---|---:|---|
| 15:54:13 | 安装版 Release `8533aaf` | 3593 | SIGABRT |
| 16:02:38 | 安装版 Release `8533aaf` | 10191 | SIGABRT |
| 16:18:28 | 冻结 Debug `88793de` | 19112 | SIGABRT |

三个报告均指向主线程 `NSUndoManager _prepareEventGrouping`、`WebKit::WebViewImpl::registerEditCommand`；安装版 UUID `DF480220-44A8-3365-9E5E-A600229943C1`，Debug UUID `B9982535-FA91-377F-A6B0-2396EEAE3BEB`，与对应二进制核对一致。仅凭栈不裁定根因。实际用键盘写入这项本应是 F1-S2 的主路径，因崩溃没有真实保存的笔记可供重启验证。即使 C2.11 四轮全过，本条仍明确失败。

### 另一个待定位现象：WebDAV 恢复后阅读主区旧错误未清除

安装版实际打开本机 WebDAV 来源，目录与图像读取成功。停服后出现连接失败和重试按钮，App 仍能操作。恢复本机服务后在错误页点击「重试」，16:24:40 服务端返回两个 PROPFIND 207，书架显示三本书，但约 0.9 秒后的同一阅读窗口仍显示原连接错误及重试按钮。主控核对窗口截图，确认书架确有三本而主区仍是错误页。后来从书签另行打开 Book-B 可正常读页。该次未确认错误页自行恢复原阅读内容，不能将重新打开当作同一次重试成功，也不能根据 0.9 秒的观测断定一定不会稍后恢复。保留 T2-S3 为部分完成、需复验。

### 结论与共同原因

```text
网页取得输入焦点 → 属于文本编辑 → 撤销不能落到文件操作
插件暂时不可用   → 暂时不显示   → 保存的位置仍须保留
同一位置打开失败 → 仍须重新加载 → 位置相等不能代表已经成功
当前页重新成功   → 对应旧失败失效 → 界面不能只认先前失败记录
```

**维持“自动与代操作验收通过，待用户手动清单”；本次没有足够证据新增必须阻塞 G5 的严重缺陷。** 四个缺陷同属扩展功能接入后，原有状态判断与生命周期边界没有全部同步的集成问题，但不是一个共同的底层故障：撤销是输入归属，布局是保存数据与显示结果混用，后两项是身份判断与失败恢复不完整。应补齐各自契约和相邻入口，现有证据不支持引入一个统管这些模块的新框架。

四条已修路径都有对应证据：`185fdc7` 的 `ReaderWindow.isEditingText`、`AppDelegate.sessionSnapshot()`、`ReaderWindowController.openBook`／`PluginCoordinator.openSource`，以及 `fb7d0d5` 的 `ViewerContainerView.retryBook()`；实机闭环分别见本报告第 3 轮 §1–2、第 4 轮 §1–2。**这证明指定路径修好，不等于同类路径已穷尽。** 以下按严重程度列出发现；P2 为应安排修正或明确跟踪的风险，P3 为文档状态问题。

### P2-1：失败恢复仍依赖入口和当前视图，尚无完整的失效契约

- **问题与证据**：`fb7d0d5` 的 `ViewerContainerView.retryBook()` 先调用 `retryFailedItems()` 再重开书；后者只选择当前浏览模式。该 diff 中 `PagedViewerView.retryFailed()` 只枚举当前 `slots`，`hasFailures` 也只看这些页槽。生产侧没有在本次 diff 中新增“同身份重新加载／成功探测后统一淘汰旧失败”的规则。来源根重试、书级重试已闭环，但非当前页、切换浏览模式后再返回、绕过该按钮的重新打开，以及晚到的旧请求结果，未由本次验收证明。第 4 轮“页列表独立观察”（本报告原第 275 行）还实际记录了主区恢复后列表仍留先前连接错误。
- **影响**：可能出现同一页在不同视图或不同重开入口下恢复程度不同。列表现象是已证实的显示不一致，但它也可能是缩略图尚未重试，不能据此断言与 `probeFailures` 同根，更不能认定整书所有页都失败。
- **建议：修恢复契约，列表现象记为遗留。** 规定失败属于哪一次加载、哪一页和哪类请求；新一轮加载使旧请求结果失效，成功结果清除它所对应的旧失败，不依赖用户再次点击局部按钮。元数据成功不能代替所有图像请求成功，缓存占位也不能证明来源恢复。下一次修复覆盖“失败后离开该页／切模式、恢复后返回”和重新打开入口；本轮不增加用户待办。按既定裁定，列表旧文案不升级为 G5 阻塞。

### P2-2：带目标页的同书打开分支仍保留旧的提前返回条件

- **问题与证据**：`185fdc7` 的 `App/Shell/ReaderWindowController.swift::openBook(_:at:restoring:)` 只给 `page == nil` 分支加了 `session.loadError == nil`。前一分支仍是“同书且能在 `book.pages` 找到目标页，就 `session.go` 并返回”，没有检查加载失败。`architecture.md:817–818` 允许缓存页先交付、再后台刷新；本报告第 3 轮 §3 也记录了已有页码而书级加载出错的状态，不能把“有页”当作“加载成功”。
- **影响**：当失败会话仍保留目标页时，带页位置的打开会只跳页而不重新加载；这是与已修无页参数分支不一致的代码条件。本次未验证具体用户入口能否触发，因此不把它报告成新增实机失败。
- **建议：修。** 两个同书快速返回分支采用一致的成功条件；失败时进入重新加载并保留目标页意图。后续用“先有页面、随后加载失败、再打开同书指定页”做最小回归，不要求重跑全量 G5。

### P2-3：保存布局已有正确模型，但持久化入口的约束没有写全

- **影响**：后续维护仍可能把暂时不可见的面板误当作删除。除已修的会话写入外，**本次未发现第二处已证实的误存代码**；两份 diff 不能证明 `layout.json`、`layout-schemes.json` 的所有写入路径都已核对。第 3 轮的六次停启／重启也未覆盖“停用期间另存或覆盖布局方案”。
- **建议：修文档契约；相邻路径记为覆盖遗留。** 三个保存出口统一以保存布局为依据，显示布局只用于呈现；明确暂不可用与用户主动移除的区别。会话保存各窗口的停靠区，共享浮窗由全局布局保存，避免多窗口各存一份。后续定向核对停用期间改区尺寸、保存／覆盖方案及套用后的恢复；不能仅凭本次发现要求重写停靠框架。

### P2-4：网页撤销已修阅读窗口，但浮窗与撤销执行的证据未闭环

- **问题与证据**：`185fdc7` 同步修改了 `ReaderWindow.isEditingText`、`stepUndo`、`validateMenuItem`、`windowWillReturnUndoManager` 和 `AppCommands` 的撤销启用条件；C2.11 检查真实键入、管理器归属和 `canUndo`，没有执行撤销／重做。`architecture.md:315` 明确浮动面板是共享 `NSPanel`；报告第 3 轮 §1 验证了键入和保存，§2 验证了浮窗位置，未说明在浮窗内执行键盘及菜单撤销。§3.7–3.8 也没有文本撤销与文件撤销的归属契约。
- **影响**：阅读窗口的类型判断不能直接证明独立浮窗的命令启用与响应链正确；潜在后果包括文本撤销不可用，或命令错误落入文件操作。本次没有证据判定这些后果已经发生。
- **建议：修文档契约，记为回归覆盖遗留。** 菜单启用、菜单执行和快捷键执行都须依据实际输入焦点及同一个撤销管理器，网页编辑不能因浮动而转交阅读主窗的文件撤销。后续补一个带既有文件撤销记录的停靠／浮动文本撤销与重做用例；不扩大成新增用户手动项，也不据此重开已通过的键入崩溃验收。

### P2-5：恢复可用不等于释放资源，停止能力和信任边界须进入架构契约
