# G3 全量验收：S3 数据与文件

日期：2026-11-26。冻结 main：`d415d525259c98f1bc29b9dd0b3392e3cdb8212b`。既有安装版：`79a4bc3de77bb56e8449660de446b3008cf76144`；另用冻结源码的 Release 补验真实用户数据，不替换安装版。

**结论：G3 未通过。** 执行者登记 53 项为 34 通过、10 部分完成、6 失败、3 外部环境待验。主控将缺少展开菜单屏幕证据的 DATA-05 从通过降为部分完成，最终判定 **33 通过、11 部分完成、6 失败、3 外部环境待验**。六个失败编号有重叠，主要涉及 App 网络故障后删除重试仍超时、跨卷跳过及强杀恢复自检未完成，以及文件操作四组合自检失败。Core、CLI 或其他路径的成功不关闭这些 App 失败。部分完成项和缺少外部环境项的剩余动作一并列入下方手动验收清单。

## 做了什么

- 对照[需求](../plans/requirements.md)、[路线图 S3](../plans/roadmap.md#s3-p1-数据与文件关口-g3)、S3-T1/F1、T2/F2、T3/F3 报告及所有表下留项，验收历史、书签、播放列表、虚拟书、文件操作、搜索、评分标签、EXIF 和用户数据迁移。S3-T5 无正式阶段报告，补读现存需求 worktree 的规格和阶段总结；原始场景来源及编号缺口保留在[场景清单](bench/g3-20261126/scenario-inventory.md)。53 个稳定编号含报告检查项及重叠要求，不是 53 个互不相干的产品功能；没有猜填已丢失的原 S 编号。
- `gpt-6-luna high` 检索与核对覆盖，`gpt-6.2-astra xhigh` 串行执行所有具体检查；遵守登记 `max_workers=1`。主控核对结构化证据，并用 `view_image` 检查网络占位、删除与撤销恢复、悬停切换、四星重启、永久删除确认、设置及失败横幅等实际截图后裁定。
- 验收前复核模块和变更链：资料库与文件操作通过组合根向阅读会话及持久化存储传播变化，搜索索引与图片内 XMP 分开保存，网络写入经辅助进程，导入在建服务前备份和替换。随后从冻结提交的干净副本构建，排除主工作区既有未跟踪资源；不改源码、测试、阈值、NAS 配置或系统网络配置。
- MacPro 真正前台操作系统菜单、系统文件面板、Finder、Preview 和独立弹窗；Debug 使用隔离支持目录/缓存/布局。安装版与冻结 Release 均正常启动，不传任何 `-MV…` 参数；各轮先备份真实支持目录，结束恢复并逐项核对。
- NAS 用户图库只读；写入仅在既有授权的 `macview-fileops-test/{a,b}` 内创建本轮子目录。所有断开、重挂和故障代理仅使用工作区内本轮新建挂载，不动 `~/MacViewBench/nfs`、`fileops-a/b` 或现有 SMB。MacAir 只读探查；未为跨机验收改动其真实数据。

## 架构审核

审核日期：2026-11-26。依据为本报告、[实机明细](bench/g3-20261126/live-ui.md)、[自动化明细](bench/g3-20261126/automation-details.md)，以及 [architecture.md](../architecture.md) 的 S3 契约；未读实现源码，未运行命令或补测。以下区分已观察事实、排查假设和契约建议，不将推断写成根因。

### 失败所在层级

    App 操作与自检 → 文件操作服务 → 卷调度与辅助进程 → 系统挂载 / NAS
                           ↓ 已确认的文件变更
                   组合根 → 缓存、资料库、阅读会话与搜索

| 失败 | 更可能的层级与理由 | 尚不能下的结论 |
|---|---|---|
| 网络恢复后 App 删除重试仍超时（FILE-01/07/15） | 首查 App 操作控制器与共享 I/O 调度器、辅助进程之间的恢复接续：按钮是否发出新一轮请求，是否沿用已取消请求组或旧结果，卷降级后探测是否恢复槽位，阅读与封面并发是否挤占资源。Core 对照可恢复，优先差异是长时间运行的 App 状态和并发负载。删除还经过回收目录与描述符释放，不能只按读请求排查。 | 横幅不变不能区分未派发、再次失败和显示旧结果；不能认定纯界面缺陷，也不能排除 MVIO 或挂载状态。13 秒后的首个样本不证明主线程全程响应。 |
| 跨卷“跳过”等待超时（FILE-10） | 首查操作终态与自检等待条件，再查同一 App 调度器是否受前序请求影响。服务结果区分 changes、skipped、failures、retry；跳过项不产生移动变更，也不进入重试。若只等源全部消失、变更数或完成字节，可能等不到合法终态。不过仅预置一个冲突而 20 项源全在，跳过语义不足以解释，须确认其余 19 项是否派发及失败。 | 源保留、旧目标未覆盖不能证明操作完成；CLI 的新进程、新夹具及不同缓存状态不能排除 App 服务或调度器故障。 |
| 强杀恢复未达前置（FILE-11） | 首先是验收编排层没有建立有效恢复样本：未证明记录已落盘且复制超过 32 MB，前序超时后继续，后续可能被串联污染。其次才查组合根启动恢复与卷可用性判断：net-verify 等待连接，未区分未挂载、已挂载但降级、路径识别失败和恢复执行失败。 | 不能认定恢复算法损坏或丢数据，也不能凭收尾时空 transfers.json 反推强杀时状态。CLI 的有效强杀不能关闭 App 项。 |

### 共同原因与契约缺口

共同薄弱处是“出错以后怎样进入下一轮”缺少可核对的端到端状态链：网络恢复、调度器健康、辅助进程换代、操作重试、文件变更传播、界面终态和自检判据没有在现有证据中对齐。前三项可能共享 App 内调度与恢复状态，尚无证据证明同一个底层缺陷；过期断言是另一项已确认的问题。CLI 首轮也曾超时，不能只凭新进程重跑成功锁定 App 界面。

1. **重试与降级恢复的接续不完整。** §3.2 已规定期限、stuck 槽位、降级探测、弃用辅助进程和重新开文件，§4 已规定 retry 仅含失败项；但没有明确手动重试怎样衔接健康探测、是否创建新请求组、旧结果如何失效，以及辅助进程换代后槽位与句柄怎样收敛。应补充“旧请求终结 → 新探测确认可用 → 新操作执行 → 新结果上屏”的归属；等待健康也须可见、可取消。随机不存在名字的探测成功，只证明当时能访问服务器，不保证目标可写或删除成功。
2. **超时后的写入结果需要核实。** §3.2 同时允许阻塞调用在辅助进程被弃用后仍存活，且网络写入经它执行。调用方超时不等于底层一定没有副作用；恢复后重试删除、改名或发布，应核实源、目标与传输记录，明确结果未知时如何收敛。这是待补安全契约，不是本轮已证实发生延迟写入。排他改名回退竞态、传输记录缺少发布阶段的残余风险已有明文接受，不能直接用来解释本轮超时。
3. **操作完成与传播完成界限不清。** §4 的 FileProgress 未说明跳过、失败怎样计入完成；也未写明 App 成功、部分成功、全部跳过、失败、取消的统一终态。应以 perform 返回结果结束操作，再按需等待本批变更处理，不能只等计数或源消失。appliedFileChanges 已规定处理顺序，但与具体操作的对应关系及失败可见性仍需明确，防止操作结束和界面更新互相等待。
4. **启动恢复缺少可解释的等待状态。** §3.2 与 §4 规定异步恢复及 completed/pending/failed 汇总，却未明确 pending 的逐项原因、卷恢复后谁再次触发、是否与新操作互斥。应保留记录并显示具体等待原因；自检在强杀前核实持久记录、临时文件与实际字节，前置不成立就停止该链。不要靠调大统一超时掩盖状态缺口。
5. **资料库的成功保证有文字不一致。** §3.6 称广播时已可读新位置；§4 却明确 library.apply 失败时只记日志、仍广播且不重试，允许文件与旧引用长期不一致。前者应限定为迁移成功时成立，并决定是否提供可见错误与重新对账。本轮真实移动、撤销和三处引用迁移成功，没有证据表明此失败分支参与网络超时；不能据此判资料库为根因。
6. **搜索、评分与导入应保持各自边界。** 索引在卷降级时允许保留部分结果，条目齐全不能代替 finished 与 failures；评分成功须分别核实文件校验、rewritten 变更及缓存/索引更新，不能只看星形控件。导入在建服务前备份替换并可回滚，本轮没有证据指向它导致文件操作失败。不过 §4 规定导入保留 transfers.json、启动又自动恢复移动，仍需明确二者的启动顺序和忙碌互斥；归档冲刷也不自动等于文件写入已结束。这是契约核对方向，不主张为本轮失败重构归档模块。

### 修复优先级

- **P1，G3 放行前先完成：定位正常 App 删除重试的完整链路。** 同一窗口、同一挂载保留故障前状态，关联操作轮次、请求组、卷健康与在途/stuck 数、辅助进程代次、I/O 阶段、返回结果和界面终态；服务对照使用同一故障时序，并补 App 并发负载对照。先区分未派发、等待资源、实际 I/O 超时和旧结果回写，再修所属层，不先调期限、阈值或重建整个服务。
- **P1，接着关闭跨卷与恢复阻塞：** 独立运行两种冲突策略，核对跳过终态及其余非冲突项；前项失败即停止强杀链。记录落盘且实际复制超过门槛后才杀隔离 App，重启逐项核恢复原因、哈希、源删除、临时项和记录清理。证实共享调度状态残留则统一修 MVIO；若只是自检等待条件错误，修自检后重新取得 App 实证。
- **P2，可先做的小修：** 英文断言与当前本地化语义对齐，页序只核仍有效的产品要求；保留真实事件路径，单独复验首次模态框与焦点不稳定，再跑文件操作四组合。恢复可信反馈，但不替代前两项。
- **P2，随对应修复补契约：** 明确重试轮次、跳过进度、恢复 pending 和变更传播失败语义，校正资料库成功保证范围。索引终态、真实 NFS 元数据重试及导入与未完成传输互斥按各自留项核对。MacAir、Windows、真实来源缺失继续保留环境待验，不由架构推理代判。

架构判断：现有分层仍合理，优先补齐故障恢复在各层间的接续与可观测证据，无依据推翻资料库、搜索或归档设计。**G3 仍未通过**；推断需由对应实现核查及同环境 App 复验确认。
