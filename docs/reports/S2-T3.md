# S2-T3 验收问题修复

## 范围

针对 S2-T2 的修改前场景定位并修复问题；修改前证据在 `bench/round1/`。基于 `7e42358a838516dcbe9f18a729ca271852beeadd` 的首轮独立验收有 3 个通过、8 个环境不满足、2 个因调试响应超时未验证，见 [验收检查记录](bench/S2-stage3-checks.json)。两项超时的原 JSON 已另存 `bench/round2/`。

工具修复后在 `26cf278` 定向复验 `main-thread`，脚本判定通过：主线程 5145 个样本，5028 个有已知符号，图片读取与 ImageIO 解码为 0；另 4 次系统辅助功能本地化、符号辅助描述或 HIToolbox 初始化的文件操作，原栈见 `bench/S2-T2-main-thread.json`。录制中 3524 个事件产生 666 次位置变化，但窗口未保持前台，60 秒只有 40 帧，不能替代 120 Hz 前台帧时间验收。先前通过的 3 个场景及 247 项测试保留 `7e42358` 原证据。

`26cf278` 的 `memory-30min` 已完整运行 1801.606 秒且未出现调试响应超时，采得 1632 个样本、1066 个动作。按 elapsed 排除前 300 秒，1353 个样本的中位数为 2,002,010,112 字节，范围为 1,659,895,808–2,726,199,296 字节，最大偏差 36.173%，超过 ±10%；`leaks` 报告 416 项、19,936 字节，退出码 1。此场景未通过，原因待核查；不能将独立预算的架构差异直接认作常驻内存波动根因。见 `bench/S2-T2-memory-30min.json`。

## 内存诊断与交回

`leaks` 的 416 项分为三个 `NSXPCConnection` 根循环，分别为 139、139、138 项，协议是 `LNDaemonApplicationInterface`，连接为 `com.apple.linkd.autoShortcut`；栈中有 Foundation 对连接的强捕获及 AppIntents 的 interruption handler。记录中没有 MacView 类型或源码分配栈，应用也没有直接调用 AppIntents 或 `NSXPCConnection`，现有证据不足以定位应用代码。这不改变 `leaks` 非零的验收结果。

821.585 秒的常驻内存峰值约 2.726 GB，到 822.554 秒降至约 2.087 GB，之后约为 2.068 GB。观察支持工作集快速释放，不能据此将峰值归因于持续泄漏；`leaks` 报告的 19,936 字节也无法直接解释峰值比中位数多出的 724,189,184 字节。末态 `vmmap` 只是一个快照：IOSurface 驻留约 787.8 MiB、malloc zone 驻留约 333 MiB、只读库驻留约 807.6 MiB，并未覆盖峰值；缺少峰值时各层实际占用，无法确定来源。原始数据和栈见 `bench/S2-T2-memory-30min.json`，摘要见 `bench/S2-stage3-checks.json`。

目前没有证据支持局部修复。交设计侧继续设计工作集和独立预算，并在后续采集峰值时各层占用、定位峰值及泄漏；不调整预算或过滤峰值。

只读持有链检查发现：全书及相邻书预取会启动管线生命周期任务，`WorkLimiter` 限制作业数但等待队列没有字节预算；排队的衍生件或缩放闭包可能持有基础 IOSurface，这些活动及排队引用不随 L0/L1 淘汰释放，消费者取消后衍生件仍按现有生命周期完成。这些约束需纳入工作集预算设计，但缺少 821 秒时的队列和分配记录，不能据此认定峰值原因。静态检查缓存弱前链、共享工作完成清理和位图 retain/release 配对，未见可直接修复的永久循环。

## 缩略图交付

按阶段 3 的判定规则，测量可见缩略图完整调用时等待衍生件的比例：本地 55 项后台积压、30 个样本中，等待 P95 为 275.943 ms，完整调用 P95 为 652.869 ms，占 42.27%，超过 20%；NFS 积压占 7.98%。因此前台取得基础图并缩放后提前返回，衍生件沿用管线生命周期在后台写入；冷缩略图预取仍等待同一工作中的衍生件写完，保持预取完成的含义。

同等条件下可见调用 P95：本地 652.869 → 353.130 ms，NFS 835.739 → 641.108 ms。测量条件、样本及前后对照见 [缩略图判定证据](bench/S2-T3-thumbnail-decision.json)。三个依赖衍生件落盘的既有测试改为等待写入完成；受影响的 MVMedia、MVPipeline、MVReading 共 62 项现有测试通过，零警告。新旧测试数据不能代替完整场景最终验收。

## 其他修复与对照

- 首屏缩略图状态：修改前本地 12/20、NFS 14/20 次取得样本；可见区为空时通知被跳过，视图出现或绘制时重新核对并补发。本轮环境不满足，无有效样本，尚不能判定修复效果。
- 分块取消：修改前请求 4、移开后取消 0；现在滚动时立即取消移出视口的在途块，停止后再补发新块。本轮请求 4、取消 4，通过；前后场景脚本亦有调整，不能仅将数值变化归因于产品代码。见 `bench/round1/S2-T2-tiles-cancel.json` 和 `bench/S2-T2-tiles-cancel.json`。
- 首图场景修正测试前提：关闭全部预取、隐藏面板并排除打开时的初始页，测量未预载的不同页面端到端显示；第一轮 P95 为 159.574 ms，与调整条件后的结果不能直接视为同条件性能对照。
- 第一轮 `main-thread` 样本为 0 不可信。重新解析旧 trace 中带符号的主线程栈后有 4057 个样本，其中 3548 个含 `CFRunLoop` 或 `NSApplication`，图片读取和 ImageIO 解码为 0，另有一次系统 CoreUI 主题 `open`。这只说明该次旧录制，不代替最终场景结论。第一轮 `settle` 为 0 个样本的直接原因是导出的 os-signpost 表没有行；最终仍无样本时应标记未验证。诊断方法与数据见 [旧录制解析证据](bench/S2-T3-trace-diagnosis.json)。
- 内存旧轮线索：前 300 个样本之后波动约 19.5%；旧样本未按 1 Hz 采集且无逐样本 elapsed，不能将其当作精确排除前 5 分钟后的结论。`vmmap` 显示 IOSurface 约 2.0 GB、malloc 驻留约 710 MB、只读库驻留约 576 MB，能解释约 3.4 GB 驻留的主要构成；`leaks` 报告 416 项但尚无归因。这些均是修改前的线索；之后 `7e42358` 上因调试响应超时未完成 30 分钟，而 `26cf278` 定向复验已完成并未通过。见 `bench/round1/S2-T2-memory-30min.json`。

## 第一次验收后的工具修复

本轮 `main-thread` 的连续滚动已返回，但之后为读取辅助状态发出的 `state` 超时，录制脚本退出；`memory-30min` 的旧记录缺少失败命令和阶段，原因尚未确定。短诊断没有复现原内存超时，不能据此断言产品主线程冻结已解决。[诊断证据](bench/S2-T3-timeout-diagnosis.json) 保留旧 JSON、短测条件和限制。

定位确认 Python 3.9 的两个进程 `monotonic` 分别约为 0.180、0.138 秒，同期 Mach 时钟约为 159153、159154 秒；旧 `phase.json` 使用进程原点，不能与 Instruments 跨进程时间对齐。修复后录制阶段改用 Mach 时钟，响应超时仍使用 `monotonic`。录制失败时先等待 xctrace 保存再退出；自动滚动响应携带 `responsiveScrolling` 等状态，不再为辅助状态单独发送尾部 `state` 请求。

内存场景仅在浏览模式确需变化时切换，超时时保留命令、阶段、目标 PID、部分样本与现场；这些改动改善复验和定位，不证明原超时根因。`FileSettingsStore.global()` 所在类型不是 actor，未发现其导致超时的证据，也没有据此改变调度。修复后 20 次 `state` 短测最大 3.063 ms，优化 Debug 构建零 Swift 警告，88 项判定检查通过；正式场景复验结果见上文。
