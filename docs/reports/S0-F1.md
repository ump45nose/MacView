# S0-F1 画布引擎技术验证

任务文档：[S0-F1](../plans/tasks/S0-F1.md)。2026-11-01，MacPro（M1 Pro，内建 ProMotion 屏，120 Hz）。

## 结论

- 方案可行，S1-F3 沿用“NSScrollView + 图层池”。用触控板真实滚动 1 万项瀑布流时，帧时间 P99 = 8.33 ms：1629 帧中 7 帧卡顿，卡顿比 1.5 ms/s。达到验收的 P99 ≤ 8.3 ms。
- 图层数量有上界：全程最多 55 个图层，期间有 694 个项先后进入可见区并加载缩略图。图层数由可见区决定，与总项数无关。
- 主线程开销很小：
  - 滚动时每次更新图层分配的 P99 是 0.11–0.14 ms。
  - 改变宽度时 1 万项全量重排的 P99 是 0.54 ms，最长 1.2 ms。
- 用显示链接逐帧设置滚动位置的自动场景，不适合作为卡顿验收的依据：空白对照（不建任何项的图层）在惯性阶段也有 17.5 ms/s 的卡顿。自动场景只用来回归引擎自身的开销。
- 给 S1-F3 的调整（已写入 architecture.md §3.8）：
  - 图层内容只用已解码、IOSurface 支撑的图像。
  - 每帧设置图层内容的数量有限额。
  - 卡顿验收用真实的触控板输入。

## 做了什么

- 测试窗口（只在 Debug 构建中，菜单“调试 › 画布测试”）：
  - `App/Debug/CanvasView.swift`：
    - 砌体布局按列二分查找可见项。
    - 只为可见区上下各加一屏余量内的项分配图层，滚出范围的图层回收复用。
    - 缩略图在后台向 MockImagePipeline 请求，回到主线程只设置 `contents`；滚出范围时取消请求。
  - `App/Debug/CanvasTestWindow.swift`：
    - 测试数据是 1 万个确定性的合成项，宽高比按固定规则生成。
    - 两种管线延迟：快速（400 张/秒，延迟 20 ms）、NAS 首访（2.5 张/秒）。
    - 自动场景与对照变体（见下文）。
    - 结果 JSON 的路径由 `-MVCanvasTestReport` 指定。
- 录制与汇总：
  - `scripts/canvas-test.sh <结果目录> [变体…]`：
    - 构建打开优化（`-O`）的 Debug 配置，测试窗口只在 Debug 中编译。
    - 对每个变体用 Instruments 的 Animation Hitches 模板录制自动场景，再汇总。
  - `scripts/canvas-hitches.py <录制> <结果 JSON | -> [输出]`：
    - 导出录制中 MacView 的帧、hitch、提交（update）与渲染（render）表。
    - 用显示链接时间戳（与 mach_absolute_time 同一时基）把录制切成阶段，再逐阶段统计。
    - 传 `-` 时，整段录制作为一个阶段，用于手动滚动的录制。

## 测量方法

- 自动场景（`-MVCanvasTestAutorun YES`）：
  - 窗口放在刷新率最高的屏幕上，由该屏的显示链接驱动。
  - 准备 1 秒后依次运行三个阶段：

    | 阶段 | 时长 | 动作 |
    |---|---|---|
    | 快速拖动 | 6 秒 | 6000 pt/s，每 1.5 秒换向 |
    | 惯性滚动 | 10.5 秒 | 3 次甩动，初速 15000 pt/s，每毫秒衰减到 0.998 |
    | 改变窗口尺寸 | 6 秒 | 宽度在 800–1400 pt 之间，周期 2 秒 |

- 对照变体（`-MVCanvasTestVariant`）：
  - `full`：完整引擎。
  - `noImages`：分配图层但不加载缩略图。
  - `empty`：不分配项的图层，只剩滚动本身。
- 手动录制：
  - 打开测试窗口（快速延迟、full 变体），录制 40 秒。
  - 期间用户在触控板上快速来回拖动，再甩动几次让它惯性滑行。
- 帧时间的定义：
  - 每个上屏的帧记为一个刷新间隔（8.33 ms）。被 Instruments 判为 hitch 的帧，再加上 hitch 的时长。
  - 内容不变时 App 不提交新帧。这段空闲不算帧时间，因此不用相邻两帧上屏的间隔。
- 卡顿比：每秒的 hitch 总时长（ms/s）。Apple 的分级是 < 5 良好，5–10 需要关注，> 10 严重。
- 录制前断开了 60 Hz 的外接显示器。外接显示器是主显示器时，所有 App 的显示链接都只有 60 Hz，内建屏上也一样（用探针确认过）。

## 分析

- 滚动阶段，自动场景的卡顿不来自引擎：
  - empty 不建任何项的图层，惯性阶段仍有 18 个 hitch，帧时间 P99 同样是 16.7 ms。
  - 卡顿的帧，提交和渲染都和正常帧一样便宜。
  - 显示链接回调本身是准时的（间隔 P99 8.33 ms）。
  - 推断：在显示链接回调里设置滚动位置，绕开了 NSScrollView 自己的滚动路径（responsive scrolling），提交的时机不稳定。真实触控板滚动走系统路径，同样的引擎卡顿比只有 1.5 ms/s。
- 同一配置的两次录制差别很大：本次之前的一次 full 录制，快速拖动有 71 个 hitch（98 ms/s）。那次屏幕上还有其他在动画的窗口。所以自动场景的 hitch 数只能做粗略对照。
- 设置图层内容是引擎中唯一明显的开销：
  - 快速拖动时 full 的提交 P99 是 7.70 ms，noImages 是 1.78 ms。
  - Mock 的合成图来自位图上下文，Core Animation 在提交时要复制并上传它。
  - 真实管线输出已解码、IOSurface 支撑的图像（S1-T3 的验收项），这部分开销会小得多。
  - 突发到达时，还要按帧限额设置内容，避免一次提交里塞进几十张图。
- 改变窗口尺寸的卡顿主要来自窗口改尺寸本身：
  - empty 的卡顿比（256 ms/s）反而最高，而重排只要 0.5 ms。
  - 每帧用 `setFrame` 改窗口尺寸会让窗口重建后备存储，这不在画布的控制范围内。
  - requirements.md §5 只对滚动有要求。用户拖动改尺寸时的表现，留到 S1-F3 用真实操作再看。

## 证据

- 命令：

  ```
  scripts/canvas-test.sh <结果目录>            # full、noImages、empty 三个变体的自动场景
  xcrun xctrace record --template 'Animation Hitches' --time-limit 40s --output manual.trace \
    --launch -- build/DerivedData-profile/Build/Products/Debug/MacView.app/Contents/MacOS/MacView -MVCanvasTest YES
  python3 -I scripts/canvas-hitches.py manual.trace - S0-F1-trackpad.json
  ```

- 结果：
  - `docs/reports/bench/S0-F1-trackpad.json`：手动录制。
  - `docs/reports/bench/S0-F1-{full,noImages,empty}.json`：自动场景，含 App 侧统计。
- 录制文件每个约 900 MB，不入库。
- `make build` 零警告，`make test` 通过。

## 依赖

无新增。脚本只用 macOS 自带的 python3 和 Xcode 的 xctrace。

## 与任务文档的偏差

- 验收以触控板的手动录制为准，自动场景作对照。原因见“分析”。
- 增加了 noImages、empty 两个对照变体，用来区分引擎开销和滚动本身的开销。
- 录制用的是快速延迟（400 张/秒），图片到达最密集，设置图层内容的压力最大。NAS 延迟下，同一时间到达的图片更少。

## 未决问题

- S2-T2 的验收工具要驱动真实的滚动路径。合成滚轮事件需要辅助功能权限，按约定不授予。可选做法：
  - 经调试接口，在 App 内向 NSScrollView 发送带阶段的滚动事件。
  - 继续用手动录制。
  - 由 S2-T2 实测后选定。
- 用户拖动改窗口尺寸时的帧时间没有测，留给 S1-F3。
