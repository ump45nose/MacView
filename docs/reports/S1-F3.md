# S1-F3 画布引擎正式版

任务文档：[S1-F3](../plans/tasks/S1-F3.md)。2026-11-01，MacPro（M1 Pro，内建 ProMotion 屏，120 Hz）。

## 结论

- 正式引擎在 S0-F1 的“NSScrollView + 图层池”上完成：四种布局、锚点保持、可见范围回报、渐进取图与每帧限额、选择与键盘、捏合、错误标记与重试。测试窗口改用正式引擎，S0-F1 的实验实现已删除。
- 布局与锚点是纯计算，放在新模块 MVLayout，15 个单元测试通过（C5.1）。
- 自动场景的 App 侧统计（C5.4）在四种布局下都满足：滚动更新 P99 ≤ 0.276 ms（要求 ≤ 0.5），全量重排 P99 ≤ 0.47 ms（要求 ≤ 1）。改变窗口尺寸期间，1864 次带锚点的重排中，锚点项离开视口 0 次。
- 滚动停止后可见项的请求（C5.3）：四种布局各 8 次停走加 3 次改尺寸，停止后的请求延迟 P99 和最长都是 0；`settled` 距停止最长 55.3 ms。
- 四种布局的 Instruments 录制已完成（`scripts/canvas-test.sh`），结果是 `bench/S1-F3-{masonry,grid,verticalStrip,horizontalStrip}.json`。
- 风险：自动场景中，部分布局的停走和改尺寸阶段帧时间 P99 为 16.67 ms，高于 C5.2 的 8.3 ms，见“证据”。C5.2 以用户的触控板录制为准。
- 未完成：C5.2 需要用户用触控板录制，步骤见“给用户的录制步骤”。

## 做了什么

- `Packages/MacViewKit/Sources/MVLayout/CollectionLayout.swift`（依赖 MVFoundation、MVSettings，不依赖 AppKit）：
  - 砌体：列数由 `itemExtent` 决定，每项放进最矮的一列，查询时按列二分。
  - 网格：边长为列宽的正方形单元。位置与宽高比无关，所有项都排。
  - 纵向条、横向条：横截长度取 `itemExtent` 与视口可用长度中较小的一个（传 `.infinity` 即适合视口），居中。横向条右开时第 0 项在最右，内部用阅读坐标，输出时翻转。
  - 只排已知宽高比的最长前缀。已排部分的宽高比不变时，在尾部追加；变了就从头重排。
  - 锚点：
    - `leadingAnchor(in:)`：前沿落在视口内的项中最靠前的一个。用于宽度、尺寸、种类和方向的变化。
    - `reorderAnchor(in:selected:)`：选中项，没有时取中心项。用于整体重排。
    - `viewportOrigin(restoring:)`：恢复锚点。
  - `index(moving:_:)`：方向键按画面几何找相邻项。
- `App/Canvas/CanvasView.swift`：引擎视图，是 NSScrollView 的子类，可以直接嵌入。
  - 图层池：只为可见区前后各加一屏余量内的项分配图层，滚出余量即回收，请求随之取消。
  - 重排：
    - 视口尺寸、`itemExtent`、`kind`、`direction` 变化时新建布局并恢复锚点。
    - 连续的重排（拖动改窗口尺寸、捏合）共用最初的锚点，用户滚动后清除。
  - `setItems`：
    - 前面的项身份不变（追加项或补宽高比）时，原布局只追加，已排的项不动。
    - 否则视为整体重排：按身份换算选中项，以选中项或中心项为锚点。
  - 滚动停止（50 ms 没有变化）时 `settle`：
    - 统计可见项请求的发出时间，补发缺少的请求，以及尺寸变大后不够清晰的请求。
    - 发出 signpost `settled`。
    - 范围有变化时，通过 `onVisibleRangeChange` 回报 `CanvasVisibleRange(visible:margin:)`。
  - 交互：
    - 单击选中，⌘ 切换，⇧ 从焦点项选到点击项，双击或回车调用 `onActivate`。
    - 方向键移动选中项，并滚到可见。
    - 捏合改 `itemExtent`（80–640），通过 `onItemExtentChange` 回报。
  - 错误：单项失败时，图块上居中显示 `exclamationmark.triangle`；点击该项即重试。
- `App/Canvas/CanvasImageLoader.swift`：取图。
  - 缩略图来源用 `thumbnail(for:maxPixel:)`；显示图来源用 `image(for:target:)` 的渐进流，网格中宽高比未知的项退回缩略图。
  - 按项在屏幕上的像素尺寸请求。
  - 按内容身份去重和缓存（NSCache，256 MB）。渐进交付时只换成更精确或更清晰的图。
  - 结果先排队，由文档视图的显示链接每帧最多设置 `contentsPerFrame`（8）个图层内容。
  - 图层内容用 `RenderedImage.surface`，没有时（Mock）用 CGImage。
- 测试窗口 `App/Debug/CanvasTestWindow.swift`：
  - 控件：布局、方向、缩略图尺寸、图像来源和延迟可切换；另有“倒序”（整体重排）和“宽高比重新到达”（乱序分批到达）两个按钮。
  - HUD 显示图层、请求、回报的范围和锚点检查。
  - 每 1000 项注入一个读取失败，用来看错误标记。
  - 启动参数 `-MVCanvasTestLayout <布局>`。
  - 自动场景在 S0-F1 的三个阶段之外加了“停走”（移动 0.35 秒、停 0.4 秒，共 8 次）。“改变窗口尺寸”阶段，横向条改高度，其余布局改宽度。
- 脚本：
  - `scripts/canvas-test.sh <结果目录> [布局…]`：依次录制四种布局，加 os_signpost instrument，用 `caffeinate -d -u` 保持亮屏，输出 `S1-F3-<布局>.json`。
  - `scripts/canvas-hitches.py`：新增按阶段统计 signpost 的滚动停止（`settles`、`settleRequestLatencyP99/Max`、`settleEventDelayMax`）。

## 证据

- `make build`：通过，零警告。
- `make test`：全部通过，零警告。其中 MVLayoutTests 有 15 个测试：
  - 四种布局的位置与内容尺寸；
  - `items(in:)` 与暴力扫描逐项一致（五种布局与方向组合，各 50 个随机矩形）；
  - 只排最长前缀；
  - 宽高比乱序分批到达：每一步与上一步逐项比较，已排的项不动（右开横向条比较到右端的距离），最终与一次排完的结果相同；
  - 改动已排项的宽高比会从头重排；
  - 锚点：宽度变化保持偏移；跨种类后锚点项在视口内；跨过视口前沿的项按比例换算；恢复时收紧；重排时取选中项或中心项；右开横向条向左增长时锚点不动；
  - 键盘移动：网格、砌体、右开横向条、纵向条。
- 自动场景（C5.4），各阶段的 App 侧统计，单位 ms：

  | 布局 | 来源 | 快速拖动滚动更新 P99 | 惯性 P99 | 停走 P99 | 重排 P99 / 最长（次数） | 锚点重排 / 离开视口 |
  |---|---|---|---|---|---|---|
  | 砌体 | `bench/S1-F3-masonry.json` | 0.142 | 0.119 | 0.276 | 0.47 / 0.71（450） | 450 / 0 |
  | 网格 | `bench/S1-F3-grid.json` | 0.122 | 0.113 | 0.097 | 0.166 / 0.178（450） | 450 / 0 |
  | 纵向条 | `bench/S1-F3-verticalStrip.json` | 0.132 | 0.048 | 0.049 | 0.122 / 0.264（449） | 449 / 0 |
  | 横向条 | `bench/S1-F3-horizontalStrip.json` | 0.137 | 0.114 | 0.083 | 0.127 / 0.158（515） | 515 / 0 |
  | S0-F1 | `bench/S0-F1-full.json` | 0.11 | 0.14 | — | 0.54 / 1.18（669） | — |

  - 命令：`scripts/canvas-test.sh docs/reports/bench [布局…]`，用 `-O` 构建。砌体和网格的 JSON 来自重录，纵向条和横向条来自第一轮。7 次录制中有 3 次 os-signpost 表为空（砌体 1 次，网格 2 次），这些录制已丢弃；脚本现在遇到这种情况会报错退出，不产出 JSON。
  - 滚动更新最初按帧调用 `perform(afterDelay:)` 和 `cancelPreviousPerformRequests` 去抖，砌体的 P99 为 0.24 ms。改成一个推迟触发时间的计时器后，降到 0.12–0.18 ms。
- 滚动停止后的请求（C5.3），Instruments 加 os_signpost：四种布局各 8 次停走加 3 次改尺寸，停止后可见项的请求延迟 P99 和最长都是 0，`settled` 距停止最长 55.3 ms。
  - 停止时刻取最后一次 `updateVisible` 的开始。延迟为 0，表示可见项的请求在滚动中就已发出（`request` 事件都早于停止时刻）。
  - 滚动停止 50 ms 后回报可见范围，交给预取计划。
- 自动场景的帧时间 P99（Instruments），单位 ms，括号内是 hitch 数。这不是 C5.2 的判定数据（C5.2 用触控板录制），但其中的 16.67 ms 是风险：

  | 布局 | 快速拖动 | 惯性 | 停走 | 改变窗口尺寸 |
  |---|---|---|---|---|
  | 砌体 | 8.33（7） | 8.33（2） | 8.33（0） | 8.33（2） |
  | 网格 | 8.33（1） | 8.33（2） | 8.33（1） | 16.67（16） |
  | 纵向条 | 8.33（4） | 8.33（3） | 16.67（19） | 16.67（11） |
  | 横向条 | 8.33（3） | 8.33（2） | 16.67（14） | 16.67（7） |

  - 快速拖动和惯性阶段四种布局都是 8.33 ms。
  - 停走（纵向条、横向条）和改尺寸（网格、纵向条、横向条）阶段是 16.67 ms，即这些阶段超过 1% 的帧错过一次刷新。如果用户的触控板录制也是这个结果，C5.2 不达标，需要分析。
- 图层：峰值 47–54（砌体）、66（网格）、11（纵向条）、19（横向条），与项数无关。

## 给用户的录制步骤（C5.2）

前提：断开 60 Hz 的外接显示器，解锁屏幕并保持亮屏，命令都在 worktree 根目录执行。

1. 先构建优化版本（`scripts/canvas-test.sh` 用的是同一份）：

   ```
   xcodegen generate --quiet
   xcodebuild -quiet -project MacView.xcodeproj -scheme MacView -configuration Debug \
     -destination "platform=macOS,arch=$(uname -m)" -derivedDataPath build/DerivedData-profile SWIFT_OPTIMIZATION_LEVEL=-O build
   ```

2. 手动录制。每种布局 `L`（masonry、grid、verticalStrip、horizontalStrip）各录两段。trace 写到 worktree 之外：

   ```
   APP=build/DerivedData-profile/Build/Products/Debug/MacView.app/Contents/MacOS/MacView
   TRACES=$(mktemp -d)
   # 滚动 30 秒：窗口出现后，在触控板上快速来回拖动，再甩动几次让它惯性滑行（横向条左右滑）
   xcrun xctrace record --template 'Animation Hitches' --time-limit 30s --output $TRACES/manual-$L-scroll.trace --launch -- $APP -MVCanvasTest YES -MVCanvasTestLayout $L
   # 改尺寸 20 秒：先滚到中间，然后来回拖窗口右下角（横向条拖上下边）约 15 秒；结束前截下 HUD 最后一行“锚点：N 次重排，离开视口 M 次”
   xcrun xctrace record --template 'Animation Hitches' --time-limit 20s --output $TRACES/manual-$L-resize.trace --launch -- $APP -MVCanvasTest YES -MVCanvasTestLayout $L
   python3 -I scripts/canvas-hitches.py $TRACES/manual-$L-scroll.trace - docs/reports/bench/S1-F3-trackpad-$L.json
   python3 -I scripts/canvas-hitches.py $TRACES/manual-$L-resize.trace - docs/reports/bench/S1-F3-resize-$L.json
   ```

3. 录制后清理留下的停止进程：xctrace 退出后 MacView 可能停在 T 状态，执行 `pkill -9 MacView`。

4. 判定：
   - 滚动的 JSON 中 `phases[0].frameTimeP99` ≤ 8.33 ms。
   - 改尺寸的帧时间写进本报告。
   - HUD 上“离开视口”为 0，同时目测锚点项始终在视口内。
   - 录制文件很大，不入库。

## 自行决定的事项

- MVLayout 的接口与 stage-5 草案的差别，完整接口见 architecture.md §4：
  - `init(kind:viewportSize:itemExtent:spacing:direction:)` 用视口尺寸代替 `width`。横向条需要高度；`contentSize` 也直接作为文档尺寸，沿滚动方向不小于视口，右开横向条才能贴右对齐。
  - 锚点方法拆成两个：`leadingAnchor(in:)` 用于尺寸和种类变化，`reorderAnchor(in:selected:)` 用于整体重排，两者规则不同。`viewportOrigin(restoring:) -> CGPoint?` 去掉了 `viewportSize` 参数（布局已持有），锚点项还没排时返回 nil。
  - `LayoutAnchor` 增加 `extent`：项跨过视口前沿时按比例换算偏移。其余情况偏移按点保持，恢复时收紧到整项可见（项比视口长时铺满视口）。
  - 新增 `count`、`columnCount`、`CollectionLayoutKind.isHorizontal` 和 `CaseIterable`，以及键盘用的 `LayoutMove` 与 `index(moving:_:)`。
- 网格不依赖宽高比，所有项都排；只排最长前缀的规则适用于砌体和两种条。
- 视口尺寸的任何变化（包括沿滚动方向）都做全量重排，P99 不到 1 ms，没有另设只改内容尺寸的路径。
- 缩略图逐项调用 `thumbnail(for:)`，没有用批量的 `thumbnails(for:)`：项滚出余量时要逐个取消，批量流只能整体取消。
- 可见范围通过闭包回报 `visible` 与 `margin` 两个范围，由调用方接到 `ReaderSession.visibleRangeChanged`（S1-T6 已实现）或面板的预取。测试窗口只显示回报值，没有会话。
- 删掉了 S0-F1 的对照变体 `noImages`、`empty`：正式引擎不带测试用的模式。
- 自动场景加了“停走”阶段，为 C5.3 提供滚动停止的样本。

## 与任务文档的偏差

- 缩略图请求不再像 S0-F1 那样封顶 1024 像素，而是按项的实际像素尺寸请求。砌体列宽 230 pt 时，最长约 1840 像素。场景中加载的图从 S0-F1 的 694 张降到 180–210 张。推断原因：Mock 合成大图更慢，更多请求在滚出余量后被取消；未单独验证。
- Mock 的图没有 IOSurface，引擎此时用 CGImage，提交开销与 S0-F1 相当。真实管线接入后才能验证只用 IOSurface 的路径。
- architecture.md §4 和 roadmap 按 stage-5 的分工在 W5.4 同步，不在本工作包内。

## 问题

- 显示器睡眠与锁屏：本机是远程使用，录制途中显示器睡眠，20:58 起锁屏。显示链接随之停止：
  - 自动场景卡住，或者跨过整个阶段，进而触发测试窗口结果统计的越界崩溃（已修：阶段起点改为定长数组，被跳过的阶段记为空）。
  - xctrace 退出后，崩溃的 App 进程停在 T 状态，占着资源（已手动结束）。
  - `caffeinate -d -u` 只能唤醒未锁屏的显示器。解锁屏幕后重跑，四种布局的录制已完成。
- `make test` 中有两个 MVIO 测试需要 `Fixtures/local/generated` 下的大夹具，worktree 里原本没有。已用 `mvbench fixtures` 在 worktree 内生成（不入库），清单没有变化。
- Swift Testing 的 `#expect` 直接比较 CGFloat 表达式与 Double 时，两边相等也会判失败；测试里改为显式转成 Double 再比较。
